# write

writing-kitのguidelineに従って、指定された形式（箇条書きまたは散文）の文書を書く。

## 前提

- 本skillのディレクトリを基準にした `../../guidelines/common_guideline.md` を必ず読み込む
- 形式と文体に応じて、次のいずれかを読み込む：
    - 箇条書き → `../../guidelines/style_bullet.md`
    - 散文（です・ます調） → `../../guidelines/style_desu_masu.md`
    - 散文（だ・である調） → `../../guidelines/style_da_dearu.md`

## 進め方

1. **書く条件を確認する**。次の3つを、依頼や素材から読み取る。読み取れないものはユーザーに質問する — 黙ってどれかをデフォルトにしない
    - 形式：箇条書きか散文か
    - 文体：散文の場合のみ、です・ます調かだ・である調か。箇条書きはstyle_bulletが文体を定めているので確認しない
    - 読者：誰が、どこで（Confluence / developers blog / noteなど）読むか。common_guidelineの「読者の前提」を守るには、読者が何を知っているかが分かっている必要がある

2. **guidelineを読み込む**。common_guidelineと、形式・文体に応じたguidelineを読む

3. **内容の不明瞭な部分を詰める**。入力（トピック、素材、下書き、セッションでの議論、既存の文書など）を読み、内容に不明瞭な部分がないかを確かめる。例えば次のような場合：
    - 主張が決まっていない
    - 命題の帰属（定説か、研究の帰結か、自分の推論か）が判断できない
    - 抽象的な主張に当てる具体例が入力にない
    - 論の流れとして複数の組み方が考えられる

    不明瞭な部分があれば、grillingなどを使って、ユーザーと認識が揃うまで詰める。具体例や帰属を勝手に補わない

4. **全体を書く**。guidelineに従って文書全体を書き上げる。書いている途中で新たに不明瞭な部分が見つかった場合は、そこで書くのを止めて手順3に戻る

5. **書いたものをチェックする**：
    - 入力にある命題を漏らしていないか
    - 入力にない主張を付け足していないか
    - 執筆前の議論やセッションの中でしか通じない言葉が残っていないか（common_guidelineの「読者の前提」）
    - common_guideline・形式別のguidelineに反する表記・言い回しが混入していないか

6. **出力して直す**。書き上げた文書を出力し、ユーザーのフィードバックを受けて直す

## 進め方の注意

- 節ごとに確認しながら進めるのは、ユーザーが求めた場合だけにする
- 既存の箇条書きの文書を散文に書き直す場合は、bulletを本文の文章に機械的に変換するのではなく、bulletの命題を散文でどう述べるかを考えて書く。命題の帰属と論の順序は保存する。子bulletは親bulletの命題の列挙・詳細・根拠なので、散文でもその関係が伝わるように書く

## 出力

- 文書そのものを出力する（前置きの説明文を長々と付けない）
